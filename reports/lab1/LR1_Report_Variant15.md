# Лабораторная работа № 1
## Выявление требований к порталу и выбор инструментального средства

**Дисциплина:** Практикум по разработке корпоративного портала
**Вариант:** 15 — Университет. Центр аккредитации и независимой оценки качества (АНОК)

## 1. Предметная область

Центр АНОК проверяет учебные планы образовательных программ университета. Учебный план содержит перечень дисциплин, семестры, трудоёмкость, часы, формы контроля и подразделения, отвечающие за дисциплины.

Портал предназначен для хранения этих сведений и предоставления к ним удобного доступа сотрудникам Центра АНОК и подразделений университета. В учебном прототипе данные хранятся в локальной базе SQLite, а работа с ними выполняется через веб-интерфейс.

## 2. Основные процессы

1. Выпускающее подразделение подготавливает учебный план.
2. План передаётся в АНОК на проверку.
3. Сотрудник АНОК просматривает структуру плана и проверяет основные показатели: общий объём, распределение по семестрам, блоки дисциплин, практику и ГИА.
4. По результатам проверки фиксируется состояние плана и замечания.
5. План может быть передан на согласование и утверждение.
6. При необходимости изменения оформляются служебной запиской с указанием прежних и новых значений.
7. Утверждённые планы доступны для просмотра пользователям портала.

В рамках учебного прототипа реализуются хранение и просмотр данных, страницы проверки, согласования, служебных записок и справочников. Полноценная юридически значимая электронная подпись, подключение внешней системы университета и промышленная ролевая инфраструктура в прототип не входят.

## 3. Акторы системы

| Актор | Назначение |
|---|---|
| Сотрудник выпускающего подразделения | Подготавливает учебный план и служебную записку на изменение. |
| Сотрудник реализующего подразделения | Проверяет изменения, относящиеся к закреплённым дисциплинам. |
| Эксперт АНОК | Проверяет учебный план и фиксирует результат проверки. |
| Руководитель АНОК | Рассматривает результаты экспертизы. |
| Проректор по учебной работе | Участвует в согласовании учебного плана. |
| Секретарь Ученого совета | Фиксирует сведения о рассмотрении плана. |
| Ректор | Утверждает учебный план. |
| Студент или преподаватель | Просматривает утверждённые учебные планы. |
| Администратор | Поддерживает справочники и данные портала. |

## 4. Варианты использования

Диаграмма вариантов использования приведена на рисунке.

![Диаграмма вариантов использования](../../diagrams/use_case_diagram.png)

### UC-1. Просмотр учебного плана

**Актор:** сотрудник университета, эксперт АНОК, студент или преподаватель.
**Результат:** пользователь видит сведения об образовательной программе, статусе плана и дисциплинах по семестрам.

### UC-2. Проверка учебного плана

**Актор:** эксперт АНОК.
**Результат:** пользователь получает сведения о контрольных показателях плана и фиксирует результат проверки.

### UC-3. Просмотр маршрута согласования

**Актор:** участник согласования.
**Результат:** пользователь видит этапы согласования, ответственных лиц и состояние каждого этапа.

### UC-4. Работа со служебной запиской

**Актор:** выпускающее или реализующее подразделение, сотрудник АНОК.
**Результат:** пользователь видит причину изменения и значения «Было» / «Стало».

### UC-5. Работа со справочниками

**Актор:** администратор или сотрудник АНОК.
**Результат:** пользователь просматривает стандарты ФГОС, образовательные программы, подразделения и компетенции.

## 5. Функциональные требования

### FR-1. Учебные планы

- FR-1.1. Портал должен хранить учебные планы и связывать их с образовательными программами.
- FR-1.2. Для плана должны храниться учебный год, версия, статус и общий объём.
- FR-1.3. Для дисциплины должны храниться блок, название, семестр, зачётные единицы, часы, форма контроля и ответственное подразделение.
- FR-1.4. Пользователь должен иметь возможность просматривать план целиком или по выбранному семестру.

### FR-2. Проверка ФГОС

- FR-2.1. Портал должен хранить параметры стандарта ФГОС.
- FR-2.2. На странице проверки должны отображаться основные показатели учебного плана.
- FR-2.3. Результат проверки должен быть представлен в виде состояния и перечня замечаний.

### FR-3. Согласование

- FR-3.1. Для учебного плана должны быть предусмотрены состояния от черновика до утверждения.
- FR-3.2. Для каждого этапа должны отображаться ответственный и состояние этапа.
- FR-3.3. Портал должен хранить сведения о выполненных этапах согласования.

### FR-4. Служебные записки

- FR-4.1. Служебная записка должна быть связана с учебным планом.
- FR-4.2. В записке должны храниться номер, дата, причина и подразделения-участники.
- FR-4.3. Изменение должно описываться прежним и новым значением.
- FR-4.4. Для записки должен отображаться статус обработки.

### FR-5. Справочники и аудит

- FR-5.1. Портал должен предоставлять просмотр стандартов ФГОС, образовательных программ, подразделений и компетенций.
- FR-5.2. Портал должен хранить сведения о действиях и событиях, относящихся к работе с документами.

## 6. Нефункциональные требования

- NFR-1. Приложение должно запускаться локально без отдельного сервера базы данных.
- NFR-2. Данные должны храниться в SQLite с внешними ключами и связями между основными сущностями.
- NFR-3. Веб-интерфейс должен корректно отображаться на компьютере и мобильном устройстве.
- NFR-4. Страницы просмотра должны открываться без длительного ожидания на учебном наборе данных.
- NFR-5. Приложение должно использовать параметризованные SQL-запросы и экранирование выводимых значений.
- NFR-6. Структура приложения должна позволять в дальнейшем заменить SQLite на серверную СУБД без изменения предметной модели.

## 7. Выбор инструментального средства

Для учебной реализации выбран следующий стек:

- Python 3;
- Flask;
- SQLite;
- HTML и шаблоны Jinja2;
- CSS и готовые визуальные классы интерфейса.

SQLite выбран потому, что это встроенная файловая СУБД, не требующая отдельной установки и настройки сервера. База переносится вместе с проектом одним файлом, что удобно для лабораторной работы и проверки результата. SQLite поддерживает таблицы, индексы, внешние ключи и транзакции, поэтому достаточен для учебного прототипа портала.

Flask выбран как небольшой веб-фреймворк с понятной маршрутизацией и минимальным количеством обязательных компонентов. Это позволяет сосредоточиться на предметной области и получить запускаемый результат без лишней инфраструктуры.

Выбранный стек предназначен именно для учебного прототипа. Для промышленной эксплуатации потребовались бы отдельные меры по авторизации, резервному копированию, нагрузке и подключению серверной СУБД.

## Заключение

В работе описана предметная область Центра АНОК, определены акторы и основные варианты использования, сформированы функциональные и нефункциональные требования. Для реализации учебного прототипа выбран стек Python, Flask и SQLite. Выбор позволяет получить простой, переносимый и проверяемый результат без отдельного сервера базы данных и без функций, которые не реализуются в рамках данной лабораторной работы.
