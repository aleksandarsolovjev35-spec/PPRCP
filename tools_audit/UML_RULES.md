# UML 2.5 — рабочая памятка для диаграмм ЛР № 1 и № 2

Документ фиксирует правила нотации для диаграммы вариантов использования ЛР1
(`tools_audit/gen_use_case.py`) и пяти диаграмм ЛР2 (`tools_audit/gen_lab2_uml.py`).
Источники: OMG UML 2.5.1 (formal/2017-12-05),
uml-diagrams.org, Sparx Systems UML 2.5 guide, Visual Paradigm / Lucid UML guides.

## 0. Общие принципы

1. **Одна диаграмма — один вопрос.** Компоненты: «из каких модулей состоит система и через
   какие контракты они связаны». Развёртывание: «на каких узлах это работает».
   Классы: «какие сущности и правила предметной области». Последовательность: «в каком
   порядке объекты обмениваются сообщениями в конкретном сценарии». ER-схема: «как это
   хранится в таблицах».
2. **Согласованность между диаграммами.** Имена компонентов ↔ артефактов ↔ классов ↔
   таблиц должны соответствовать друг другу (HttpKernel → `portal/server.py` →
   `CurriculumService` → `curriculums`).
3. **Каждый элемент нотации несёт смысл.** Нельзя ставить ромб «на всякий случай»,
   кратность «1..*» вместо «0..*», стрелку зависимости там, где есть интерфейс.
4. **Читаемость:** текст не пересекается линиями, линии не проходят через тела фигур,
   подписи стоят рядом со своим элементом.

## Варианты использования (ЛР1)

- Предмет моделирования — **портал Центра АНОК**: именованный прямоугольник, внутри которого находятся эллипсы прецедентов. Снаружи — девять акторов из § 3 ЛР1, включая две роли, для которых нет учётной записи в демонстрационной БД.
- Имя прецедента описывает действие и его цель, а не название экрана. Сплошная линия без стрелки связывает участвующего актора с прецедентом. Она не обозначает передачу данных или порядок шагов; кратности здесь не требуются.
- `«include»`: пунктир с открытым наконечником **у включаемого** прецедента. В каждой экспертизе UC-4 проверяется лимит экзаменов UC-5.
- `«extend»`: такой же пунктир **от расширяющего к базовому** прецеденту. UC-6 дополняет UC-4 оформлением замечаний только при нарушениях; порядок подписания плана этими связями не моделируется.

Пересборка: `python3 tools_audit/gen_use_case.py`. Проверка без записи файлов: `python3 tools_audit/check_use_case.py` (Pillow и шрифты DejaVu). Проверяются состав ролей и концы связей, в том числе направление `include`/`extend`, положение фигур относительно границы системы, пересечения отрезков, эллипсов и измеренных границ надписей. После пересборки проверить также **рисунок 1 в ЛР1** и **слайд 4 в презентации ЛР7** в масштабе страницы.

## 1. Диаграмма компонентов

| Элемент | Нотация |
|---|---|
| Компонент | прямоугольник + ключевое слово `«component»` + пиктограмма (два выступающих прямоугольника) |
| Предоставляемый интерфейс | «шарик» (кружок) на линии от границы компонента |
| Требуемый интерфейс | «гнездо» (полукруг, открытый в сторону компонента) |
| Сборочный разъём (assembly connector) | «гнездо» потребителя, **надетое на** «шарик» поставщика |
| Зависимость | пунктирная стрелка с открытым наконечником, стереотип `«use»` |
| Порт | небольшой квадрат на границе компонента (если у компонента несколько точек взаимодействия) |
| Подсистема | компонент со стереотипом `«subsystem»` / граница (boundary) вокруг группы компонентов |

Правила:
- интерфейс — это **контракт**, а не класс: имя существительное-роль (`IPortalPages`, `IPersistence`);
- у компонента может быть несколько предоставляемых и требуемых интерфейсов;
- шарик и гнездо ставятся **в одной точке** соединения (классический вид разъёма),
  а не на разных концах линии; шарик принадлежит поставщику, гнездо — потребителю;
- внутри блока компонента — только ключевое слово `«component»`, имя и пиктограмма;
  поясняющего текста (расшифровок «что делает») в блоке нет — обязанности описывает отчёт;
- зависимости `«use»` — только там, где формального интерфейса нет.

## 2. Диаграмма развёртывания

| Элемент | Нотация |
|---|---|
| Узел | трёхмерный блок (перспектива куба) |
| Устройство | узел со стереотипом `«device»` |
| Среда исполнения | узел со стереотипом `«executionEnvironment»` (в рус. литературе — «execution environment») |
| Артефакт | прямоугольник с «загнутым углом» и ключевым словом `«artifact»` |
| Манифестация | пунктирная стрелка `«manifest»` от артефакта к компоненту, который он реализует |
| Путь связи | ассоциация между узлами, подписанная протоколом (`«protocol» TCP 3306`) |
| Спецификация развёртывания | `«deployment spec»` — файл конфигурации, привязанный к среде |

Правила: артефакты **вкладываются** в узел/среду; компонент не «разворачивают» напрямую —
он манифестируется артефактом; среда исполнения вкладывается в устройство. Узел и среда — это
**контейнеры**: линия `«manifest»` от артефакта к компоненту законно пересекает их рамку, поэтому
геометрический аудит (`check_geometry.py`) считает нарушением линию внутри *листового* блока
(артефакт, компонент, таблица, класс), но не внутри рамки узла/среды.

## 3. Диаграмма классов

| Элемент | Нотация |
|---|---|
| Класс | прямоугольник: имя / атрибуты / операции |
| Видимость | `+` public, `−` private, `#` protected, `~` package |
| Атрибут | `имя : Тип [кратность] = значение по умолчанию` |
| Операция | `имя(параметр : Тип) : ТипРезультата` |
| Ассоциация | линия; **кратность на обоих концах** + имя роли |
| Композиция | **закрашенный** ромб у «целого» (часть не существует без целого) |
| Агрегация (shared) | полый ромб — семантика в стандарте не определена, поэтому **не используется** |
| Генерализация | линия с полым треугольником у родителя |
| Зависимость | пунктирная стрелка |
| Абстрактный класс | имя полужирным курсивом + свойство `{abstract}` (ёлочки `«…»` — только для стереотипов) |
| Примечание | прямоугольник с загнутым углом + пунктирная привязка |

Правила: кратность читается «сколько экземпляров класса на **противоположном** конце
связано с одним экземпляром этого класса» и стоит **рядом со своим концом** (а не у дальнего
колена обхода); наследуемые атрибуты объявляются один раз в классе-владельце и не
переобъявляются у наследников; имена параметров операций — осмысленные (`curriculum`,
`event`), а не односимвольные (`c`, `e`); ромб композиции — только на одном конце;
навигационные стрелки ставятся, только если направление важно; абстрактность помечается
свойством `{abstract}` и курсивом, а не стереотипом `«abstract»` (такого стереотипа в
стандарте нет); в UML-типах используются примитивы `String`, `Integer`, `Boolean`, `Real`,
`UnlimitedNatural` и перечисления предметной области (`DocType`, `BlockType`, …), а не
`Text`/`CString`.

## 4. Диаграмма последовательности

| Элемент | Нотация |
|---|---|
| Актор | фигурка человека |
| Линия жизни | пунктир вниз от головы участника |
| Период активности | узкий прямоугольник на линии жизни |
| Синхронное сообщение | сплошная линия + **залитый** наконечник |
| Асинхронное | сплошная + открытый наконечник |
| Возврат | **пунктир** + открытый наконечник |
| Создание/уничтожение | пунктир к новой голове / крестик на линии жизни |
| Фрагмент | рамка с пятиугольным ярлыком оператора: `alt`, `opt`, `loop`, `par`, `break` |
| Условие (guard) | `[условие]` в ветви `alt` / в ярлыке `loop` |

Правила: у каждого синхронного вызова — возврат; ярлык `alt` — на рамке, условия — на
ветвях; `loop` охватывает **все** линии жизни, участвующие в повторяемом фрагменте;
порядок линий жизни слева направо = порядок инициации.

Геометрия (то, из-за чего возникают «наезды»):
1. Стрелка сообщения начинается и заканчивается **на ребре полосы активности**, а не в её
   середине и не на оси линии жизни: иначе линия протыкает прямоугольник активации.
   Полоса активации **начинается ровно на линии входящего синхронного вызова** — наконечник
   упирается в её верхний угол; если начать полосу выше (на 20–25 px), стрелка приходит
   в боковую грань и «висящий» кусок полосы читается как ошибка. Полоса **заканчивается
   ровно на линии возврата** — возврат выходит из её нижнего угла (со стороны вызываемого),
   а не из пустоты на 6–8 px ниже: иначе на стыке получается ступенька. Возврат в
   вызывающего тоже упирается в ребро его полосы.
   **Полоса активации = «объект выполняется».** Между запросами объект простаивает,
   поэтому сквозная полоса на всю диаграмму недопустима: на каждый запрос рисуется
   отдельный блок (страница — 5 блоков по числу действий пользователя: `1–14`,
   `15–22`, `25–26`, `27–28`, `29–33`; контроллер — 3). Одна полоса на всю диаграмму
   читается как «объект занят непрерывно», что неверно.
2. Подпись сообщения ставится только в **свободный коридор между соседними линиями жизни**;
   если текст не влезает в коридор — переносится на 2–3 строки. Подпись не должна попадать
   на полосу активности, на чужую линию жизни или на голову участника.
3. Вложенный фрагмент (например, `loop` внутри ветви `alt`) рисуется с отступом внутрь
   родительской рамки, а его ярлык не пересекается с первым сообщением операнда.
   **Порядок наложения:** контур рамки — под линиями жизни и полосами активности, а
   вкладка оператора — непрозрачная и **поверх** них; иначе полоса активации режет слово
   `loop` и перечёркивает текст условия. Условие ветви `alt` ставится под разделителем
   операнда, а не над ним.
4. **Пунктиры не должны сливаться.** Возврат сообщения — чёрный короткий пунктир
   (штрих 5, пробел 4, толщина 1.5) с открытым наконечником. Рамка фрагмента и
   разделитель операндов — **светло-серый** длинный пунктир (штрих 11, пробел 7,
   толщина 1.1). Линия жизни — средний серый (штрих 6, пробел 5). Одинаковых пунктиров
   на диаграмме быть не должно: иначе связь не отличить от границы области.
5. **Парность связей.** Каждый синхронный вызов закрыт ровно одним возвратом к тому же
   вызывающему, причём по принципу стека: возврат закрывает последний открытый вызов.
   Возврат к актёру обязателен — иначе его запрос «висит» до конца диаграммы. Уведомление,
   которое никто не ждёт, — **асинхронное** сообщение (сплошная линия, открытый
   наконечник), а не возврат.
6. **Ветви `alt` сходятся.** Обе ветви обязаны вернуть управление в одно и то же место,
   иначе продолжение после фрагмента не определено. Если каждая ветвь заканчивается
   возвратом пользователю, ветвь «отказ» завершает сценарий, и продолжение после
   фрагмента относится только к успешной ветви — это допустимая и правильная модель.
7. Семантика: если подписание маршрута возможно только при успешной проверке, `loop`
   ставится **после** `alt` и помечается в шапке условием «только при `[нарушений нет]`».
   Вкладывать `loop` в операнд `alt` нельзя: второй операнд оказывается **ниже** цикла по
   оси времени, и его возвраты попадают за пределы полос активации вызывающих объектов.
   Проверка автоматизирована: `tools_audit/check_sequence_links.py`.

## 5. Реляционная схема (нотация «воронья лапка», IE/Crow's Foot)

| Элемент | Нотация |
|---|---|
| Таблица | прямоугольник: имя, список столбцов с типами |
| Первичный ключ | пометка `PK` (и подчёркивание в классической нотации) |
| Внешний ключ | пометка `FK` |
| Обязательность | `NOT NULL` — полужирный тип, иначе допускается NULL |
| Сторона «многие» | «воронья лапка» |
| Сторона «один» | поперечная черта |
| Необязательность связи | кружок на конце линии |
| Кратность | подпись `0..*`, `0..1`, `1` у концов |

Правила: линия идёт от `FK` дочерней таблицы к `PK` родительской; FK, допускающий NULL,
даёт `0..1` на стороне родителя; связь читается «родитель 1 —— 0..* потомков»; кратность
стоит у своего конца; линии прокладываются только по свободным каналам между столбцами и
строками (без диагоналей и «пеньков»), а пересечения устраняются перекомпоновкой маршрута,
а не разрывами линий.
UML-нотация классов и ER-нотация таблиц не смешиваются: схема БД — отдельный рисунок.

## 6. Чек-лист приёмки каждой диаграммы

1. Все элементы нотации использованы по назначению (нет «декоративных» ромбов/стрелок).
2. На диаграмме классов и схеме БД кратности стоят у своих концов связей; роли ассоциаций классов — у соответствующих классов.
3. Ни один текст не перекрыт линией или другим текстом.
4. Линии не проходят сквозь прямоугольники сущностей.
5. Имена согласованы с другими диаграммами и с кодом (`portal/…`, `schema.sql`).
6. Есть заголовок, подзаголовок с указанием нотации и легенда.
